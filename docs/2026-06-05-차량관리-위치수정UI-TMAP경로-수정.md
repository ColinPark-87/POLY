## 이슈 1 — 정류장 위치 수정 시 검색 패널이 지도를 가림

### 증상
세션설정·호차설정 후 좌측 상단 ETA 카드 → 정류장 클릭 → **정류장 위치 수정**에서
주소를 검색해 지점을 잡으려 하면, 검색에 쓰던 팝업이 최소화되지 않고 화면 전체를
덮은 채 남아 **뒤의 지도가 보이지 않아** 핀으로 위치를 확인·조정할 수 없었다.

### 원인
ETA 카드 경로의 정류장 수정 팝업(`stopPopup`)이 **화면 전체를 덮는 모달**이었다.
`RouteMapView.tsx` (수정 전):
```jsx
<div className="fixed inset-0 z-[80] bg-black/40 flex items-center justify-center p-4" ...>
  <div className="bg-white ... max-w-sm max-h-[82vh] ...">
    {renderStopExpanded(stop.name)}   // ← 주소 검색 포함
```
주소를 검색하면(`searchStop` → `applyCandidate`) 지도가 해당 좌표로 이동하고
드래그 가능한 후보 핀이 지도에 찍히지만, 이 모달(`bg-black/40` 딤 + `inset-0`)이
지도를 그대로 덮고 있어 핀과 지도가 보이지 않았다.
(같은 파일의 "새 정류장 추가 모달"은 좌표 지정 중 작은 바로 축소되는 패턴이
이미 있었으나, 이 정류장 수정 팝업에는 적용돼 있지 않았다.)

### 수정
후보 위치 조정 중(`candidateStop === stop.name`)에는 전체화면 모달 대신
**하단 컴팩트 시트**로 자동 축소하도록 변경.
- 어두운 배경(`bg-black/40`) 제거 → 지도 상단이 보이고 핀 드래그 가능
- 바깥 컨테이너 `pointer-events-none` + 시트 카드만 `pointer-events-auto`
  → 시트를 제외한 지도 영역에서 핀 조작 가능
- 시트 안의 검색 결과 목록(여러 후보 선택)·"이 위치로 저장"은 그대로 유지
- 후보가 잡히면 기존 상단 플로팅 바("핀을 끌거나 지도를 눌러 위치 조정 / 저장·취소",
  `:3355`)가 함께 떠 저장 동선이 자연스러워짐
- 위치 조정 상태가 아닐 때는 **기존 전체화면 모달 그대로** (비파괴)

수정 위치: `RouteMapView.tsx` `stopPopup` 렌더 블록 (정류장 클릭 팝업).

## 이슈 2 — TMAP 경로가 정류장 순서대로 돌지 않음 (대치폴리매그넷 유치부 6호차)

### 증상
정류장 승·하차 순서대로 **마커 숫자(①②③…)는 정상으로 뜨는데**, 차량 도로 경로가
그 정류장들을 **지나치지 않고 그냥 도착지로 직행**해서, 순서대로 도는 모양이 안 나옴.
정류장이 많은 유치부 6호차에서 발생.

### 원인
TMAP `routes` API의 `passList`(경유지)는 **최대 5개**만 지원한다.
`app/api/tmap-route/route.ts` (수정 전):
```js
const waypoints = stops.slice(1, -1)
body.passList = waypoints.slice(0, 5)...   // ← 6번째 이후 경유지가 조용히 누락
```
정류장이 7개(시작1 + 경유5 + 도착1)를 넘으면 **6번째 이후 중간 정류장이 잘려서**
TMAP에 전달되지 않았다. 마커 번호는 프론트(`routeStopsByBus` 순서)에서 매기므로
정상이지만, 도로 경로는 잘린 정류장을 건너뛰고 도착지로 직행 → "지나치지 않고
그냥 들어오는" 증상.

### 수정
정류장 목록을 **7개 단위(경유 5개)로 분할**하되 인접 구간이 경계 정류장 1개를
공유(overlap)하도록 잘라, **구간별로 TMAP를 호출한 뒤 좌표를 순서대로 이어붙이도록**
변경. 이제 정류장 수와 무관하게 모든 정류장을 순서대로 통과하는 경로가 그려진다.

- 신규 순수 함수 `lib/utils/tmap-chunk.ts`의 `chunkStops()`로 분할 로직 분리
  (단일 정류장만 남는 꼬리 구간을 만들지 않음 — 각 구간 정류장 ≥2 보장)
- `route.ts`는 구간을 순서대로 호출, 경계 중복 좌표 제거 후 연결,
  `time`·`distance` 합산
- 한 구간이 실패해도 나머지 구간은 살려 가능한 만큼 경로 표시(`partial` 플래그)
- **정류장 7개 이하 노선은 기존과 100% 동일하게 단일 호출** (비파괴)
- 응답에 `segments`/`okSegments`/`partial` 메타 추가(프론트는 추가 필드 무시)

수정/추가 파일:
- `app/api/tmap-route/route.ts` (구간 분할 호출로 재작성)
- `lib/utils/tmap-chunk.ts` (신규, 분할 순수 함수)
- `tests/tmap-chunk.test.ts` (신규, 단위 테스트 5개)

### 참고: 순서 정확도(데이터 측)
정류장 순서는 `routeStopsByBus`에서 **탑승시간순**으로 정렬된다
(`RouteMapView.tsx:642`). 시간이 비어 있는 정류장은 맨 뒤로 밀리므로,
순서가 어색하면 각 정류장의 **운행 시간이 설정돼 있는지** 확인 필요.
이 정렬 로직은 다른 호차에도 공통 적용되므로 이번 수정에선 건드리지 않았다
(회귀 방지). 시간만 채우면 순서가 바로잡힌다.

## 이슈 3 — 캠퍼스별 지도 중심 로딩 불안정 (중계/대치/정발)

### 증상
각 캠퍼스 계정으로 로그인해 차량관리 지도를 열면 해당 캠퍼스 위치로 중심이
잡혀 로드돼야 하는데, **대치/정발은 중계(노원) 쪽으로 로드되는 등 불안정**했다.
(중계는 항상 정상으로 보임)

### 원인
1. **하드코딩 기본 중심 = 중계**: 지도 초기화 중심이 `SCHOOL_STOP`(중계,
   37.6556·127.0686)로 고정(`RouteMapView.tsx:768`). 중계는 센터링이 실패해도
   기본값이 곧 중계라 항상 맞아 보였다.
2. **센터링이 캠퍼스명-좌표 정확 일치에만 의존**: 지도 중심을 `coords[campusName]`
   (`campuses.name`과 **정확히 같은 이름의 정류장 좌표**)에만 맞췄고, 폴백이 없었다
   (`:786~794`). 대치/정발에 그 이름의 학원 좌표가 없거나 이름이 어긋나면
   `c=null` → 센터링 실패 → 중계 기본값에 머묾.
3. **캠퍼스 전환 레이스**: `campusId`는 `/api/campus/me`에서 비동기로 도착한다.
   도착 전 잠깐 `campusId=undefined` 상태에서 좌표 로더가 **중계 기본 좌표를
   적재**(`:328`)하는데, 그 사이 센터링이 그 중계 좌표로 굳어버릴 수 있었다.
   (`campusName`은 `campuses.name`, 좌표 키는 `campus_stop_coords.stop_name`)

### 수정 (`RouteMapView.tsx`)
1. **로드 캠퍼스 추적 상태 `coordsLoadedKey` 추가**: 현재 `coords`가 어느 캠퍼스
   (`coordsKey`)의 것으로 로드됐는지 기록. 좌표 로더가 localStorage/DB 적재 직후
   `setCoordsLoadedKey(coordsKey)` 호출.
2. **센터링 게이트**: `coordsLoadedKey === coordsKey`일 때만 센터링 →
   캠퍼스 전환 중 옛/중계 좌표로 잘못 묶이는 레이스 차단.
3. **정류장 범위 폴백 추가**: 학원 좌표(이름 일치)가 없으면 **이 캠퍼스 정류장
   전체로 지도 범위를 맞춤**(`setBounds`). 정류장 1개면 그 점으로 센터.
   → 캠퍼스명-좌표 매칭이 없어도 항상 올바른 지역에 위치, 중계 기본값에 묶이지 않음.
4. 중계(비캠퍼스) 경로는 기존과 동일하게 `SCHOOL_STOP` 폴백 유지 (비파괴).

> 참고: 가장 깔끔한 정상화는 각 캠퍼스의 **'캠퍼스(학원) 좌표'를 캠퍼스명과
> 동일한 이름으로 1회 설정**하는 것. 이번 폴백으로 미설정 상태에서도 정류장
> 기준으로 안정 동작하지만, 학원 좌표를 정확히 잡아두면 1순위로 그 위치에 센터된다.

## 이슈 5 — 정류장 이동 후 저장이 남지 않음 (정발)

### 증상
정발 캠퍼스에서 정류장을 이동(드래그/위치이동)해 저장했는데, **저장이 남지 않음**
(새로고침하면 옛 위치로 돌아감).

### 원인
1. **서버가 '전체 삭제 후 재삽입'** 방식(`stop-coords` POST): 캠퍼스 좌표 전체를 지우고
   받은 좌표를 한 번에 insert. **재삽입이 실패하면**(잘못된 좌표값 한 줄 등) 삭제만 되고
   삽입은 실패 → 좌표 전체 유실 → 저장이 안 남는 것처럼 보임.
2. **클라이언트가 `res.ok`를 확인 안 함**(`updateCoords`): POST 실패해도 화면·localStorage는
   '저장됨'처럼 갱신 → 사용자는 저장된 줄 알지만 DB엔 없음.

### 수정
- **서버(`stop-coords` POST)**: 파괴적 방식 제거.
  1) 유효 좌표만 필터(NaN/null 제외 → 한 줄 오류로 전체 실패 방지)
  2) **먼저 `upsert`**(`onConflict: campus_id,stop_name`) — 실패해도 기존 데이터 보존
  3) 이번 저장에 없는(삭제된) 정류장만 골라 삭제(제거 시맨틱 유지)
  → '삭제 후 삽입 실패 → 전체 유실' 위험 제거. 7개 이하/이상 무관, 모든 캠퍼스 동일.
- **클라이언트(`updateCoords`)**: `res.ok` 확인 → 실패 시 경고 + **DB 기준으로 좌표 복원**
  (저장 안 됐는데 된 것처럼 보이는 오해 차단). 네트워크 오류도 경고.

> 비고: 운영(poly-system.vercel.app)은 이번 수정 전 코드라 기존 버그가 재현됨.
> 배포 후 정발에서 이동→저장이 정상 유지되는지 확인 필요. 만약 그래도 실패하면
> 새로 추가된 경고창에 서버 오류 메시지가 떠 근본 원인을 바로 알 수 있음.
