# 2026-06-08 차량관리 — 노선 도로경로가 하차 정류장(우리은행)을 통과하지 않는 문제 수정

대상: `https://poly-system.vercel.app/campus/vehicles` (차량관리 노선 지도)
운영 중 시스템 → 수정 전 백업 선행, 보수적(기존 동작 비파괴) 수정.

신고: 유치부 1호차 **하원**에서 우리은행(하차 학생 있음, 마커 ②번 정상)을 도로 경로가
**통과하지 않고 직행**으로 그려짐.

---

## 가) 원인

### 직접 원인 — `removeRouteLoops` 휴리스틱이 하차 진입 구간을 '루프'로 오인해 접음

노선 도로경로는 다음 순서로 그려진다.
1. 프론트가 정류장 순서대로 `/api/tmap-route`(서버 프록시) 호출 → TMAP이 **모든 정류장을
   순서대로 지나는 정확한 도로 좌표**를 반환 (2026-06-05 `chunkStops` 수정으로 경유지 5개
   초과도 정상 처리됨).
2. 렌더 직전 두 휴리스틱 후처리를 적용했다(파일 내부 함수, 지도 통합 초기 v1부터 존재):
   - `trimRouteToDestination` — 도착지 이후 꼬리 정리
   - `removeRouteLoops` — 블록을 돌아 네모처럼 보이는 '루프' 접기

`removeRouteLoops`는 **"어떤 지점 i 이후에 i 근처(≈30m)로 되돌아오는 지점 j가 있으면 i+1..j를
통째로 잘라 접는다"** 는 규칙이었다(`RouteMapView.tsx` 구 :908~927).

문제: 차량이 하차를 위해 **큰길에서 빠져 우리은행에 정차하고 다시 큰길로 합류**하면,
합류점이 빠져나온 지점 근처(≈30m)가 된다. 이 '정당한 하차 진입/회차'를 루프로 보고
구간을 통째로 접어버려, 도로 경로가 우리은행을 **지나치지 않고 직행**하는 모양이 됐다.

마커 번호(②)는 폴리라인이 아니라 **정류장 좌표(`coords[stopName]`)에서 따로** 찍으므로
(`:1167`/`:1201`) 그대로 정상 — 그래서 "마커는 ②번인데 경로는 안 지나감" 증상이 됐다.

> 06-05 `chunkStops` 수정(passList 5개 초과 잘림)과는 **다른 원인**이다. 그건 서버가 정류장을
> 다 못 보내던 문제였고, 이번 건은 서버가 정확히 보낸 경로를 **프론트 후처리가 망가뜨린** 것.

### 보조 원인 — `trimRouteToDestination`의 전역 최근접 절단

구 `trimRouteToDestination`은 **전체 경로에서 도착지에 가장 가까운 점** 뒤를 모두 잘랐다.
경로 중간이 우연히 도착지 좌표(마커가 도로에서 약간 벗어난 경우 등) 근처를 지나면 거기서
잘려 경로 후반이 통째로 사라질 수 있는 잠재 버그.

## 나) 해결

후처리를 순수 함수로 분리하고(`lib/utils/route-geometry.ts`), 두 함수를 정류장 보호형으로 교체.

- **`foldSpuriousLoops(pts, stopCoords)`** — 루프를 접되, **접을 구간(i+1..j)에 실제 정류장이
  포함(≈50m 이내)되면 접지 않는다.** 정류장 없는 순수 군더더기 루프(고가/인터체인지 등)는
  종전처럼 접는다. → 하차 진입 구간 보존, 시각적 정리 기능은 유지.
- **`trimRouteToDestination(pts, dest)`** — 도착지 최근접 점을 **배열 뒤쪽(마지막 15%)에서만**
  찾아 자른다. 경로 중간이 도착지 근처를 스쳐도 거기서 잘리지 않음(실측 경로는 마지막
  정류장이 곧 경로 끝이라, 진짜 overshoot은 항상 꼬리에 있음).
- **`cleanRoutePolyline`** = 트림 → 정류장 보호 접기 (렌더 표준 후처리).

호출부(`RouteMapView.tsx`): 메인 노선 fetch(:977 부근)·등하원 동시보기 fetch(:1023 부근)
양쪽에서 `cleanRoutePolyline(pts, dest, stopCoords)` 로 교체. `stopCoords`는 그 호차의 실제
정류장 좌표 배열(학원 포함)을 넘긴다.

수정/추가 파일:
- `lib/utils/route-geometry.ts` (신규 순수 함수)
- `tests/route-geometry.test.ts` (신규, 단위 8개 — 하차 정류장 보존 회귀 테스트 포함)

## 다) 비슷한 오류 전체 노선·시스템 점검

1. **모든 호차·방향에 동일 원인 존재 (해결)** — `removeRouteLoops`는 유치부 1호차만이 아니라
   **메인 지도 전 노선 + 등하원 동시보기**에 적용됐다. 하차 진입/회차가 있는 노선은 어디든
   정류장이 접힐 수 있었다. 두 호출부 모두 정류장 보호형으로 교체해 일괄 해결.

2. **Page 2(오늘 노선) 거리/시간(ETA)이 안 뜨거나 과소계산 (해결)** — Page 2 ETA는 브라우저에서
   **TMAP을 직접 호출**하면서 `passList.slice(0, 5)`로 잘랐다(구 :1313~1316). 두 결함:
   - (a) 브라우저→TMAP 직접 호출은 **CORS+한국 IP 제약**으로 실패 → ⏱/📏가 조용히 안 뜸.
   - (b) 경유지 5개 초과 시 잘려 거리/시간 과소계산.
   → 메인 경로와 동일하게 **`/api/tmap-route` 서버 프록시 경유**로 교체(서버가 7개 단위 분할·합산).
   동일 좌표 중복 제거도 메인과 동일 적용. (Page 2 폴리라인 자체는 의도적으로 직선 연결이라
   경로 미통과 증상과 무관.)

3. **좌표 중복 제거(5자리 ≈1m)** — 동일 좌표 정류장을 경로에서 제외(`:953~958`). 서로 다른 두
   정류장의 좌표가 **실수로 같은 값**으로 설정되면 한쪽이 경로에서 빠질 수 있다(이때는 마커가
   겹쳐 보여 식별 가능). 정상 데이터에선 영향 없음 — 현 상태 유지, 위험만 기록.

4. **부분 실패(`partial`) 플래그** — 서버는 일부 구간 실패 시 가능한 만큼 경로를 그리고
   `partial: true`를 주는데 프론트가 무시한다. 드물게 한 구간이 빠질 수 있음 → 향후 경고
   배지 후보(이번엔 미적용, 비파괴).
